# Development

Обновлено: 2026-09-15.

Единый рабочий план OmniList: важные требования, состояние реализации и следующие задачи. Пересмотрен по предоставленной пользователем стратегии `omnilist-product-strategy.md` от 2026-09-13 и текущему коду. Остальные MD сохраняются как история, а не конкурирующие планы. Конкурентные оценки из стратегии являются гипотезами, не доказанными преимуществами.

## 1. Продукт и границы

**Создать один товар → подготовить к выбранным площадкам → опубликовать из одного места.**

Readiness / Compatibility Engine делает этот сценарий работоспособным, а не заменяет его аналитической панелью. Главная ценность: показать причину проблемы, предложить безопасное действие, применить, перепроверить и опубликовать без API Explorer.

- Источники каталога: создание в OmniList и импорт из существующего магазина. По уточнению пользователя первым источником импорта становится подключённый eBay; CSV и Shopify следом. Shopify не является обязательной точкой входа.
- Первые направления публикации: eBay и Etsy. Shopify как направление остаётся в плане, но после этого сквозного сценария. Amazon и другие площадки позже.
- Общий Product хранит факты о товаре. ChannelListing хранит связь и состояние конкретного магазина. Overrides меняют представление для площадки, не исходные факты.
- Начальный publishing-пилот: физические товары без вариантов; eBay EBAY_US/USD. Для проверки двух площадок нужен товар, действительно подходящий обеим, например изделие продавца с подтверждённым происхождением.
- Начать с подходящих продавцов/товаров, а не обещать совместимость любого каталога Shopify с Etsy. Целевой сегмент ещё нужно проверить интервью и пилотом.
- Цена, остаток, изображения и доставка должны быть понятны до publish. ID, payload, templates/recipes и mappings не являются основной формой продавца.
- Заказы, синхронизация, варианты и pricing rules не удалены из исходного scope, но не блокируют исследовательский publishing-пилот. Полноценные общие реальные продажи без согласования остатков небезопасны.
- Не строим сейчас ERP/WMS, рекламу, бухгалтерию, налоги, управление возвратами, сложный repricing и десятки каналов.

## 2. Правила, уточняющие стратегию

- Разделять **готовность данных**, **допустимость товара**, **доступность проверки** и **состояние публикации**. Published не является уровнем readiness.
- Основной UI: «Готово», «Нужно заполнить», «Не поддерживается / не подходит», «Не проверено / проверка недоступна». Процент не означает вероятность успеха; текущий штрафной score не является достоверностью API-проверки.
- Отсутствие блокирующих ошибок разрешает publish даже при необязательных рекомендациях. Не заставлять доводить качество до 100%.
- Readiness относится к версии товара, конкретному подключению, окружению, рынку и версии требований. После изменений результат устаревает. Перед записью сервер перепроверяет критичные условия.
- Не показывать Etsy готовым до реализации и проверки его адаптера. Недоступность API не превращать в пустые требования или успех.
- Не угадывать состояние, изготовителя, происхождение, возраст, GTIN, сертификаты и юридически значимые сведения. Слово Handmade в описании не доказывает «I did».
- Автоисправления сначала только детерминированные, сохраняющие смысл и валидируемые по схеме. Семантические предположения требуют подтверждения; не показывать выдуманные AI confidence 94–99%.
- Issue содержит действие, но клиент не получает право записывать произвольный field/value. Сервер проверяет workspace, актуальность issue и допустимую операцию; повторное применение не должно портить данные.
- Один магазин может завершиться успешно независимо от другого. При таймауте сначала сверка, не слепой повтор создания. Repair/retry входят в P0.
- Inventory sync нельзя отмечать Enabled, пока его нет. Для пилота нужны явные предупреждения об отсутствии синхронизации и ограниченный тестовый остаток.

- Каталог сейчас на `apps/web/app/page.tsx` (`/`), отдельного `/products` page нет. Workspace товара: `apps/web/app/products/[productId]/page.tsx`.

## 5. P1 — расширение доказанного сценария

- [ ] Bulk safe fixes с preview, подтверждением семантических изменений и повторной проверкой.
- [ ] Existing listing reconciliation: точные внешние ID/SKU, затем вероятные совпадения; пользователь подтверждает fuzzy/image/variant matches, без автоматического слияния по похожему названию.
- [ ] AI category candidates / extraction с источником предложения и подтверждением; измерять качество до отображения confidence. Сохранять историю принятых/отклонённых mappings и версию taxonomy.

- [ ] Shopify как направление publish: сохранить product/variant/inventory IDs, выбрать location/publication, проверить создание/обновление без дублей.
- [ ] Pricing rules и округление поверх явного Money; никакой скрытой конвертации валюты.
- [ ] Операции каталога: поиск, фильтры, пагинация, копирование/архив и bulk editing. Вес/габариты/GTIN добавлять по потребностям поддержанных товаров и площадок.
